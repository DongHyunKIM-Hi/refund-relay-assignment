## 1. 과제 소개

쇼핑몰에서 고객이 환불을 요청하면, 쇼핑몰 서버는 여러분이 만드는 **환불 서버**에 환불 요청을 보냅니다. 환불 서버는 요청을 받아서 **외부 결제대행사**에 환불을 요청해야 합니다. 그런데 결제대행사는 이런 특징이 있습니다.

- 가끔 **실패**합니다.
- 가끔 **오류**를 냅니다.
- 가끔 응답이 **매우 느립니다**.
- 응답이 늦었는데 **사실은 환불이 이미 처리**된 경우도 있습니다.

환불이 **빠짐없이, 그리고 절대 두 번 처리되지 않도록** 서버를 설계하고 구현하는 것이 과제입니다.

**이 과제에서 보는 능력: 설계력**
정답이 하나인 문제가 아닙니다. 어떤 구조로 만들지, 왜 그렇게 결정했는지가 중요합니다. 결정한 내용과 이유는 설계 문서에 적습니다.

## 2. 여러분이 만드는 것 / 제공되는 것

| | 내용 |
|---|---|
| **여러분이 만드는 것** | 환불 서버 1개 (환불 접수 API, 환불 조회 API, DB, 처리 워커). **처음부터** 만듭니다. |
| **제공되는 것** | 가상 결제대행사 (Docker), 이 가이드, 설계 문서 템플릿, 요청 예시 |
| 스택 | Java 17, Spring Boot 4.1.1, Gradle, JPA + H2 |
| 제한 시간 | 없음 |

```
[요청을 보내는 쪽]      [여러분이 만드는 서버 : 8080]                 [제공되는 가상 결제대행사 : 9090]
Swagger / curl   ─▶    환불 접수 API   환불 조회 API                  POST /pg/refunds
                             │              │                        GET  /pg/refunds/{refundId}
                             ▼              ▼
                          DB (H2) ◀────────┘
                             ▲
                        처리 워커 ────────────────────────────────▶
```

## 3. 시작하기

1. 가상 결제대행사를 실행합니다. (`compose.yaml`이 이미지를 자동으로 받아옵니다. 파일을 따로 내려받거나 `docker load`를 할 필요가 없습니다.)
   ```
   docker compose up
   ```
2. 브라우저에서 `http://localhost:9090/swagger-ui.html`을 열어 결제대행사 API를 확인합니다.
3. 여러분의 서버는 `8080` 포트로 실행합니다. (`./gradlew bootRun`)
4. 결제대행사 주소는 환경변수 `PG_BASE_URL`로 바꿀 수 있게 하고, 기본값은 `http://localhost:9090`으로 합니다.

## 4. 알아야 할 용어

| 용어 | 뜻 |
|---|---|
| **멱등성** | 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질. 택배 송장번호로 두 번 접수해도 한 번만 배송되는 것과 같음 |
| **재시도** | 실패했을 때 다시 시도하는 것 |
| **타임아웃 (대기 시간 초과)** | 응답을 기다리는 시간을 정해 두고, 넘으면 실패로 보는 것 |
| **접수 단계** | 요청이 들어와서 검증하고 저장하는 단계. **바로 응답**해야 함 |
| **처리 단계** | 저장된 요청을 뒤에서 결제대행사에 전달하는 단계 |
| **워커** | 뒤에서 처리 단계를 담당하는 백그라운드 처리 |
| **요청 ID (`refundId`)** | 환불 요청 하나를 구분하는 고유 번호. 같은 ID는 같은 요청 |

## 5. 약속 1: 여러분의 서버 API

### 5-1. 환불 접수
`POST /api/v1/refunds`

```json
{
  "refundId": "R-1001",
  "orderId": "ORD-2001",
  "paidAmount": 10000,
  "refundAmount": 3000,
  "reason": "단순 변심"
}
```

| 필드 | 규칙 |
|---|---|
| `refundId` | 요청 ID. 필수, 1~50자. **같은 ID는 같은 요청**으로 봅니다 |
| `orderId` | 주문 번호. 필수 |
| `paidAmount` | 원 결제 금액. 필수, 1 이상. 이 값을 그대로 믿고 판단합니다 |
| `refundAmount` | 환불 금액. 필수, 1 이상 |
| `reason` | 환불 사유. 선택 |

**응답**

| 상황 | 상태 코드 | 본문 |
|---|---|---|
| 새로 접수됨 | **202** | `{"refundId":"R-1001","status":"ACCEPTED","duplicate":false}` |
| 같은 ID, 같은 내용으로 다시 요청 | **200** | 기존 결과: `{"refundId":"R-1001","status":"<현재 상태>","duplicate":true,"failureReason":<있으면>}` |
| 환불 한도 초과 | **422** | 에러 본문 (거절 기록은 `REJECTED`로 저장) |
| 같은 ID, 다른 내용 | **409** | 에러 본문 (저장하지 않음) |
| 입력 오류 | **400** | 에러 본문 (저장하지 않음) |

**에러 본문**
```json
{ "code": "REFUND_LIMIT_EXCEEDED", "message": "환불 가능 금액을 초과했습니다.", "refundId": "R-1001" }
```

| 에러 코드 | 상황 |
|---|---|
| `INVALID_REQUEST` | 입력 오류 (400) |
| `REFUND_ID_CONFLICT` | 같은 ID, 다른 내용 (409) |
| `REFUND_LIMIT_EXCEEDED` | 한도 초과 (422) |

**"같은 내용"이란**: `orderId`, `paidAmount`, `refundAmount`가 모두 같은 경우입니다. `reason`은 비교하지 않습니다.

**환불 한도 규칙**
같은 `orderId`에서 **`ACCEPTED`와 `COMPLETED` 상태인 환불 금액의 합 + 이번 `refundAmount` ≤ `paidAmount`** 이어야 합니다. `REJECTED`와 `FAILED`는 환불이 되지 않았으므로 합계에서 뺍니다.

**거절된 요청을 같은 ID로 다시 보내면**: 같은 ID, 같은 내용이므로 기존 결과(`REJECTED`, 200, `duplicate: true`)를 돌려줍니다.

### 5-2. 환불 조회
- 단건: `GET /api/v1/refunds/{refundId}` (없으면 404)
- 목록: `GET /api/v1/refunds?orderId=ORD-2001&page=0&size=20`

```json
{
  "items": [
    {
      "refundId": "R-1001", "orderId": "ORD-2001", "refundAmount": 3000,
      "status": "COMPLETED", "failureReason": null, "attemptCount": 1,
      "requestedAt": "2026-09-21T10:00:00", "completedAt": "2026-09-21T10:00:03"
    }
  ],
  "page": 0, "size": 20, "totalElements": 1, "totalPages": 1
}
```
**접수 시각 최신순**으로 정렬합니다.

### 5-3. 상태와 실패 사유

| 상태 | 의미 |
|---|---|
| `ACCEPTED` | 접수됨. 처리 대기 또는 처리·재시도 중 |
| `COMPLETED` | 결제대행사가 환불을 성공 처리 |
| `FAILED` | 재시도를 모두 소진해 최종 실패 |
| `REJECTED` | 접수 단계에서 거절 |

내부적으로 더 세밀한 상태(예: 재시도 대기)를 써도 되지만, **밖으로는 위 4개로 보여야** 합니다.

| `failureReason` | 상황 |
|---|---|
| `REFUND_LIMIT_EXCEEDED` | 한도 초과 (`REJECTED`) |
| `PG_DECLINED` | 결제대행사가 실패로 응답 (`FAILED`) |
| `PG_ERROR` | 결제대행사가 오류(5xx)로 응답 (`FAILED`) |
| `PG_TIMEOUT` | 응답 대기 시간 초과 (`FAILED`) |

마지막 시도가 실패한 원인이 실패 사유입니다.

### 5-4. 재시도 규칙
- 최초 시도가 실패하면 **최대 3회 재시도**합니다. (총 4회 시도)
- `PG_DECLINED`, `PG_ERROR`, `PG_TIMEOUT` **모두 재시도 대상**입니다.
- **재시도할 때도 같은 `refundId`를 결제대행사에 보냅니다.**
- 재시도 간격과 응답 대기 시간은 **자유**입니다. 다만 **한 건이 종결 상태(`COMPLETED`, `FAILED`)가 되기까지 60초를 넘지 않게** 설계하세요. (결제대행사가 매우 느릴 수 있으니 응답 대기 시간은 5초 안팎을 권장합니다.)
- 같은 주문의 환불이 여러 건이면 **접수 순서대로 하나씩** 처리합니다. 앞 건이 종결되기 전에 다음 건을 결제대행사에 보내지 않습니다. 다른 주문끼리는 동시에 처리해도 됩니다.

## 6. 약속 2: 가상 결제대행사

주소: `http://localhost:9090` · 자세한 명세는 Swagger에서 확인하세요.

### 환불 요청
`POST /pg/refunds`

```json
{ "refundId": "R-1001", "orderId": "ORD-2001", "amount": 3000 }
```

응답 (HTTP 200)
```json
{ "refundId": "R-1001", "result": "SUCCESS", "alreadyProcessed": false, "processedAt": "2026-09-21T10:00:03" }
```

| `result` | 의미 |
|---|---|
| `SUCCESS` | 환불 성공 |
| `FAIL` | 환불 실패 |

- HTTP **5xx**가 오면 결제대행사 내부 오류입니다.
- 응답이 **몇 초 이상 걸릴 수 있습니다.**

### 환불 결과 조회
`GET /pg/refunds/{refundId}`

```json
{ "refundId": "R-1001", "status": "PROCESSED", "amount": 3000, "processedAt": "2026-09-21T10:00:03" }
```
`status`는 `PROCESSED`(처리됨) 또는 `NOT_FOUND`(처리 기록 없음)입니다.

### 요청 ID를 알아봅니다 (중요)

| 상황 | 결제대행사의 동작 |
|---|---|
| **성공한** 요청 ID로 다시 요청 | 다시 환불하지 않고 이전 성공 결과를 돌려줌 (`alreadyProcessed: true`) |
| **실패한** 요청 ID로 다시 요청 | 환불이 안 된 것이므로 새로 처리를 시도 |
| **다른** 요청 ID | 완전히 다른 요청으로 처리 (같은 주문이라도) |

> 이 성질을 어떻게 활용해야 환불이 두 번 되지 않을지 생각해 보세요.

## 7. 시나리오

아래 시나리오가 모두 기대대로 동작해야 합니다. 시나리오는 **자가 점검 체크리스트**이기도 합니다.

### 접수 단계

| # | 시나리오 | 기대 결과 |
|---|---|---|
| S1 | 정상 환불 요청 | 바로 **202 ACCEPTED**, 저장됨. 응답은 결제대행사를 기다리지 않음 |
| S2 | 같은 ID, **같은 내용**으로 다시 요청 | **200**, 기존 결과 반환 (`duplicate: true`). 새로 저장하지 않음 |
| S3 | 같은 ID, **다른 내용** (예: 금액이 다름) | **409 `REFUND_ID_CONFLICT`**. 기존 건은 그대로 |
| S4 | **같은 ID** 요청이 **동시에 여러 건** | **정확히 1건만 저장**. 나머지는 S2처럼 기존 결과 반환 |
| S5 | 환불 금액이 결제 금액 초과 | **422 `REFUND_LIMIT_EXCEEDED`**, `REJECTED`로 저장, 사유 기록 |
| S6 | **같은 주문**에 **서로 다른 ID**가 **동시에** 요청, 합계가 결제 금액 초과 | 한도 안에서만 접수, 나머지는 거절. 합계가 한도를 넘지 않음 |
| S7 | 금액이 0 이하이거나 필수값 누락 | **400 `INVALID_REQUEST`** |

예) S6: 결제 금액 10,000원인 주문에 4,000원 환불 요청 3건이 각각 다른 ID로 동시에 들어오면, **2건 접수(ACCEPTED), 1건 거절(REJECTED)** 이어야 합니다.

### 처리 단계

| # | 시나리오 | 기대 결과 |
|---|---|---|
| S8 | 결제대행사가 `SUCCESS` | 상태 **`COMPLETED`**, 완료 시각 기록 |
| S9 | 결제대행사가 `FAIL` 또는 5xx | **최대 3회 재시도**. 계속 실패하면 **`FAILED`** + 실패 사유. 중간에 성공하면 `COMPLETED` |
| S10 | 결제대행사 응답이 너무 느림 (대기 시간 초과) | 실패로 보고 재시도. 소진 시 `FAILED` + `PG_TIMEOUT` |
| S11 | **같은 주문**의 환불 여러 건 | 접수 순서대로 **하나씩** 결제대행사에 전달. 다른 주문은 동시에 처리 가능 |

### 조회

| # | 시나리오 | 기대 결과 |
|---|---|---|
| S13 | 주문별 목록 조회 | 최신순, 페이지 나누기 (`page`, `size`, `totalElements`, `totalPages`), 상태와 실패 사유 포함 |

### 심화 (선택, 가점)

| # | 시나리오 | 기대 결과 |
|---|---|---|
| S12 | 결제대행사가 **환불을 처리하고도 응답을 너무 늦게** 준 경우 (시간 초과로 보임) | 재시도해도 **환불은 딱 1번만** 처리됨. 최종 상태는 `COMPLETED` |

| 심화 (S12) | +5 | 시간 초과 후에도 환불 1번 |

**이렇게 하면 크게 감점됩니다**
- 환불이 두 번 처리됨 (이중 환불)
- 재시도할 때 `refundId`가 바뀜
- 접수 API가 결제대행사의 응답을 기다림 (응답이 느려짐)
- 실행이 안 됨 (실행 방법이 위 규칙과 다름)

**힌트 1: 큰 구조**
